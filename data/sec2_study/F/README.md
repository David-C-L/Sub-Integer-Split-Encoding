# F: generic row-addressable fixed-width layouts, with/without bit-range knowledge (2026-10-02)

Companion to C1/C2 (encoder-agnostic entropy) and D (generic byte-stream compressors xz/zstd/
lz4/snappy). Both of those measure something that is NOT row-addressable: C1/C2's entropy
numbers aren't realised by any decoder with O(1) random access to row i, and D's compressors are
sequential LZ77-style streams (reaching row i means decompressing from the start). This batch
asks the complementary question the author asked for: how much does a plain, textbook,
**row-addressable fixed-width layout** gain from knowing the documented or data-chosen bit-range
partition, and where does its best achievable size sit relative to a generic heavyweight
compressor's whole-column size (xz, reused unchanged from `D/csv/split_measure.csv`)?

**No SIS, no planner, no cost model, no Nimble encoder anywhere in this script.** Four textbook
addressable layouts, implemented directly in numpy (`scripts/f1_addressable_layouts.py`). Local
only.

Columns, partitions, seeds: identical to C/D -- `C/scripts/structure_common.py`'s `ALL_COLUMNS`
registry (A's 22-column registry + the 2 regenerated unstructured controls
`hashed_splitmix64`/`random_uint64`, same generator/seed, already materialised in `C/data/` from
2026-10-02 -- not regenerated by this batch, reused as-is), same leading 524,288-row prefix, same
`field()` and `data_chosen_partition(k=2.0)` helpers (imported unchanged from
`C/scripts/structure_common.py`, so SPLIT_DATA's cuts are byte-for-byte identical to C1/D's).

## The four addressable layouts

Every layout gives O(1) access to row i: the decoder needs only `i`, a handful of column-level
header scalars (width, min, dictionary), and -- for the per-block FOR and for any SPLIT_* layout
-- one array index (`i // 1024` for blocks; which range's narrow field word to read is fixed at
layout-compile-time, not stored per row). No value is reordered; row i's data lives in a
fixed-size slot indexed by i, as in a real columnar page. `bits_per_value = total_bits / n`,
`n = 524288` throughout.

- **WHOLE_FBW**: fixed bit width for the whole value, `W = max(1, bit_length(max(vals)))` bits
  per row, plus a column-level header (`WIDTH_HDR_BITS = 8`, amortised) recording `W`.
- **WHOLE_FOR (global)**: subtract the column min; `Wd = max(1, bit_length(max-min))` bits per
  row, plus the min (stored at `W` bits -- safe since `min <= max < 2^W`) and the width header
  (`WIDTH_HDR_BITS = 8`), once per column.
- **WHOLE_FOR (per-1024-row block)**: same, independently per contiguous 1024-row block (last
  block may be shorter): each block stores its own min (`W` bits) and width
  (`WIDTH_HDR_BITS = 8`), then `width_block` bits/row in that block.
- **WHOLE_DICT**: only if distinct count `k <= n/2` (`DICT_MAX_DISTINCT_FRAC = 0.5`). Fixed-width
  code per row, `Wc = max(1, bit_length(k-1))` bits, plus the dictionary (`k` entries at `W` bits
  each) and a count header (`DICT_COUNT_HDR_BITS = 32`), once per column.

`WHOLE_best` = min bits/value across the 4 (DICT excluded when `k > n/2`) -- the denominator for
every gain% below, and what a schema designer would pick without bit-range knowledge.

**SPLIT_DOC / SPLIT_DATA**: for each bit range `(lo, hi)` in the documented layout (SPLIT_DOC,
13/24 columns) or the data-chosen flip-gradient partition (SPLIT_DATA, `data_chosen_partition
(k=2.0)`, all 24 columns): extract `field(vals, lo, hi)` (values confined to
`[0, 2**(hi-lo))`, so every header above is already tight for sub-ranges), independently pick the
best of the same 4 layouts *for that range alone*, and sum. One additional small header per
range, `RANGE_TAG_BITS = 2` bits (amortised over n), records which of the 4 layouts the range
uses -- the range boundaries themselves are compiled into the layout/schema, not stored per row
or per column.

**Headers counted** (all amortised, i.e. divided by n=524288, so negligible in absolute terms but
included for completeness): `WIDTH_HDR_BITS=8` (fixed width field), `DICT_COUNT_HDR_BITS=32`
(dictionary entry count), `RANGE_TAG_BITS=2` per range (which layout a range uses), plus the FOR
min itself (`W` bits, global) or `n_blocks * W` bits (per-block FOR) and the dictionary payload
(`k * W` bits). None of these is a cost-model constant reused from elsewhere in the study (not
`study_common.py`'s `HEADER_BITS_PER_SECTION`) -- they are specific to this batch's own textbook
formulas, documented above and in `scripts/f1_addressable_layouts.py`'s module docstring.

**Generic-compressor reference** (`xz_WHOLE`): reused unchanged from `D/csv/split_measure.csv`
(`compressor==xz, variant==WHOLE_best`), NOT recomputed. It is **not addressable** (xz/LZMA is a
sequential LZ77 stream; reaching row i means decompressing from the start) -- included only as
the generic-compressor size reference requested for the figure/table trade-off.

## The trade-off (the point of this batch)

- **Knowing the bit ranges helps an addressable layout, but only modestly**, and only on the
  structured/near-T1 group: SPLIT_DATA averages +17.6% over best-WHOLE-addressable on the 11
  structured columns (up to +58.2% on xmark), essentially 0 or negative on near_miss (-2.6%) and
  control (-3.8%, all <=0% as expected -- a pure noise/overhead floor, same floor D sees under
  xz). SPLIT_DOC (the *documented* partition, not the data-chosen one) is weaker still, +7.6%
  mean, because several documented field boundaries (h3/s2/morton's digit-vs-header split, e.g.
  `h3_r15` -7.1%) don't line up with where the FOR/DICT layouts actually save bits, while the
  data-chosen partition finds narrower, more profitable cuts.
- **A non-addressable generic compressor (xz) still finds far more structure than either
  addressable layout, on every group, including the controls.** xz_WHOLE averages +52.0% smaller
  than best-WHOLE-addressable on structured columns (vs. +17.6% for SPLIT_DATA), and -- the
  important asymmetry -- **+21.4% even on the control group**, where no addressable layout (with
  or without range knowledge) gains anything. This is LZ77 match-finding picking up incidental
  regularities (e.g. `tpch_orderkey`'s monotone run structure, +87.7% under xz) that a
  fixed-width per-row slot cannot represent at all, addressable or not: an addressable layout's
  slot width is fixed in advance and must cover every row's value, so it cannot exploit a
  sequential match the way a byte-stream compressor can.
- **Headline trade-off**: bit-range knowledge measurably helps a *row-addressable* layout
  (SPLIT_DATA > WHOLE_best on every structured column but one), but the gain is a fraction of
  what a heavyweight, non-addressable compressor captures on the same data. The ranges let an
  addressable layout claw back part of the redundancy xz already captures "for free" at the cost
  of random access -- never all of it, and never on data that has no bit-range structure to find
  in the first place (near_miss/control stay flat or negative under SPLIT, same direction as D's
  finding 10, but xz's absolute edge over *any* addressable layout, structured or not, is bigger
  here than the SPLIT-vs-WHOLE gap D reported for addressable-vs-addressable).

## Caveats

1. **This is not a decoder comparison.** `xz_WHOLE`'s bits/value is a real compressed-stream
   size; the 4 addressable layouts' bits/value are closed-form slot sizes from textbook formulas,
   not a built encoder. Neither pays real per-page/per-file container overhead beyond the headers
   listed above. The comparison is "what a schema designer gets for free" (WHOLE), "what they get
   if told the bit ranges, still addressable" (SPLIT), vs. "what a generic archiver gets by
   giving up addressability entirely" (xz) -- not three implementations of the same contract.
2. **Header constants are this batch's own choices** (`WIDTH_HDR_BITS=8`, `DICT_COUNT_HDR_BITS
   =32`, `RANGE_TAG_BITS=2`), documented above, chosen to be small and defensible, not tuned to
   favor any layout; they are negligible at n=524,288 regardless (<=0.001 bpv each) and do not
   change which layout wins for any column.
3. **DICT's dictionary-entry width is `W` bits (the column/range's own FBW bound), not a tighter
   bound on the *set* of distinct values.** This is conservative (never undercounts) but can make
   DICT look worse than it would with a packed/sorted dictionary; doesn't change any WHOLE_best
   winner in this run (checked against `csv/addressable_layouts.csv`'s `method` column), so not
   load-bearing for the headline numbers.
4. **FOR per-block's min header always uses the column/range's global `W` bits**, not each
   block's own (tighter) local bound -- a conservative, uniform choice across all blocks; real
   per-block-tightened headers would only ever shrink FOR_block's cost further, so this cannot be
   inflating the "SPLIT doesn't gain much" conclusion.
5. **SPLIT_DOC only exists for 13/24 columns** (the ones with a documented layout in the shared
   registry); the 3 T4 near-miss-measure columns and all 8 controls have no documented layout and
   are `NaN` in `csv/addressable_layouts.csv` for that variant, same convention as `D`.
6. **xz_WHOLE is reused, not recomputed** -- any change to `D/csv/split_measure.csv` (e.g. a
   different xz preset) would change this batch's reference column without this batch's own code
   changing; documented here so the dependency is explicit.

**Two added layouts** (F1's four are imported unchanged).
- RLE_RANK: `r` runs, run values at W bits, run end positions (exclusive) at `bit_length(n)` bits. The end array is the rank directory: row i is a binary search for the first end > i, O(log r). Headers: `WIDTH_HDR_BITS` + `DICT_COUNT_HDR_BITS` (run count).
- PFOR: per 1024-row block, min (W bits), slot width b (8), exception value width (8), exception count (11). Slots take b bits per row. Exceptions (residual >= 2^b) store position (10 bits) and full residual (block max-residual width). b in [0, we] is chosen per block to minimise bits. Row i is a slot read plus a search among the block's sorted exception positions.
- SPLIT_DATA6 and SPLIT_DOC6 take the best of six layouts per range, range tag 3 bits. Ties go to the older four layouts.
